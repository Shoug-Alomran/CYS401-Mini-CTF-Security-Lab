Introduction

Cybersecurity education entails the use of practical exercises to reinforce theoretical concepts. The CTF events are great tools in helping the learners go through realistic situations, find weaknesses, and solve security problems in order to collect flags which develop important critical thinking and technical skills.

1 · The platform

Guided challenges in technical and non-technical areas

This paper discusses a Mini Capture-The-Flag (CTF) Security Lab Platform which has been created to offer guided challenges in technical and non-technical areas. The platform provides a user-friendly graphical interface—avoiding any complexities of command lines—and offers guided challenges in four key areas:

Users go through different security situations to obtain and upload challenge flags such as insecure configurations, password security, phishing, and simple ciphers. 2.1 · Assets

Seven assets the platform has to protect

User Accounts

Individual accounts used to identify users and associate their activity with the platform.

Security importance

Accounts must be protected from unauthorized access and impersonation to ensure that activity and progress are associated with the correct user.

User Credentials

Authentication information used to verify the identity of users when accessing their accounts.

Security importance

Credentials must remain confidential to prevent account compromise and unauthorized access to the platform.

Challenge Flags

Secret values that users must discover and submit to successfully complete CTF challenges.

Security importance

Flags must remain confidential until legitimately discovered. Exposure of flags would allow users to bypass the challenge and undermine the integrity of the CTF.

Challenge Content

Security scenarios, instructions, hints, resources, and educational explanations provided for each challenge.

Security importance

Content must maintain its integrity so that challenges remain accurate, functional, and consistent with their intended learning objectives.

User Progress

Records of challenges attempted and completed by each user.

Security importance

Progress data must remain accurate and protected from unauthorized modification to ensure that users receive the correct completion status.

Scoreboard Data

Information used to represent participant scores, completed challenges, and rankings.

Security importance

Scoreboard data must maintain its integrity to prevent manipulation of scores or rankings and ensure fair results.

Underpins every asset

Database

The underlying data storage used by the platform to maintain user, challenge, progress, and other application data.

Security importance

Unauthorized access, modification, or loss of database information could compromise the confidentiality, integrity, and availability of multiple platform assets.

  • User Credentials

2.3 · Vulnerabilities

Where an attack could get in

A vulnerability refers to a flaw in a system that can be exploited by an attack resulting in harm. Vulnerabilities in the CTF Security Lab can range from those associated with authentication, input processing, access control, data protection, to system configuration. Recognizing such vulnerabilities helps in instituting security measures that prevent exploitation of such flaws.

  1. V1

    Weak Authentication Controls

    User Authentication and Accounts

    Weak authentication mechanisms may allow unauthorized individuals to gain access to user accounts and impersonate legitimate users.

  2. V2

    Improper Input Validation

    Flag Submission and User Input Forms

    Failure to properly validate or sanitize user input may allow malicious or unexpected input to affect application behavior or stored data.

  3. V3

    Insufficient Access Control

    User Accounts, Progress Records, Scoreboard, and Database

    Users may be able to access or modify information or functionality that should be restricted to other users or administrators.

  4. V4

    Insecure Flag Storage

    Challenge and Flag Validation System

    If challenge flags are exposed or stored insecurely, users may retrieve them without solving the intended challenges.

  5. V5

    Insecure Data Storage

    Database

    Improper protection of stored data may expose user information, progress records, challenge information, or other application data to unauthorized parties.

  6. V6

    Security Misconfiguration

    Web Application and Hosting Environment

    Incorrect permissions, exposed configuration information, or insecure settings may unintentionally expose sensitive information or functionality.

3.1 · Capture-the-Flag in Cybersecurity Education

Two formats, and the gap we fill

Capture-The-Flag (CTF) challenges engage learners in solving practical cybersecurity tasks to retrieve hidden flags. CTF events generally follow an Attack-Defense structure or a Jeopardy-style format that organizes standalone challenges by category.

Jeopardy-style

Our approach

Standalone challenges organized by category. The proposed platform uses a Jeopardy-style structure so beginner-level users can complete guided exercises independently.

Attack-Defense

The other common structure for CTF events.

Švábenský et al. (2021)

While CTF activities effectively build technical skills, traditional platforms often neglect human-centric topics like social engineering and security awareness. Additionally, steep technical requirements frequently deter beginners.

How our lab responds

The Mini CTF Security Lab addresses these limitations by providing a balanced, accessible curriculum that combines technical and non-technical topics.

3.4 · Related Security Incident · 1 of 3

Qatar National Bank (QNB) Data Breach

We selected three incidents from the Gulf region, each linked to one of the attacks described in Section 2.4.

Date
July 2015 (breach began); made public April 2016
Security issue
SQL injection. Analysis of the leaked data suggests the attack began through a SQL injection flaw in the bank’s website (Have I Been Pwned, 2016).
Linked attack
2.4 · Injection Attack

What happened

About 1.4 GB of internal files and customer records from Qatar National Bank were published online in April 2016. The leak exposed more than 100,000 accounts, including passwords and PINs (Have I Been Pwned, 2016; Al Jazeera, 2016).

Impact

Customers’ personal and financial data were exposed publicly, and the breach went undetected for about nine months.

Relevance to this project

Our flag submission and login forms accept user input that reaches the database. This incident shows why the platform must validate input and never build database queries from raw user input. It relates to the Injection Attack in Section 2.4.

3.4 · Related Security Incident · 2 of 3

Careem Data Breach

Date
Breach detected January 14, 2018; disclosed April 23, 2018
Security issue
Unauthorized access to stored user data. Careem did not publish the technical cause. It said passwords were encrypted and card details were kept on a separate system (Arab News, 2018).
Linked attack
2.4 · Broken Access Control

What happened

Careem, a Dubai-based ride-hailing company, announced that attackers had gained unauthorized access to the system it uses to store customer and driver data. About 14 million users across the Middle East were affected (Arab News, 2018; Tom’s Hardware, 2018).

Impact

Names, email addresses, phone numbers, and trip data were exposed. Careem hired a cybersecurity firm to investigate and advised users to change their passwords (Gulf News, 2018).

Relevance to this project

Our database stores user accounts, progress, and scores. This incident shows the need for strict access control on stored data, and for storing passwords and flags in protected or hashed form so that a leak does not reveal usable secrets. It relates to Broken Access Control in Section 2.4.

3.4 · Related Security Incident · 3 of 3

Denial-of-Service Attack on Saudi Government Websites

Date
May 2013
Security issue
Distributed denial of service (DDoS): flooding servers with requests until they stop responding.
Linked attack
2.4 · Denial-of-Service

What happened

Several Saudi government websites, including the Ministry of Interior’s site, were disabled by coordinated attacks traced to hundreds of IP addresses in several countries. The Ministry of Interior website crashed after receiving a very large number of requests and was restored in less than two hours (Al Jazeera, 2013; Gulf News, 2013).

Impact

Government services were unavailable to the public during the attack.

Relevance to this project

If an attacker floods our login or flag submission path, students lose access during a lab session. This supports request limits on submissions. It relates to the Denial-of-Service Attack in Section 2.4.

5.2 · Software Requirements

The stack: static pages, serverless backend

Frontend

HTML5, Tailwind CSS 3 (Play CDN), vanilla JavaScript (ES modules)

All 20 pages are static HTML styled with Tailwind utility classes; no framework and no build step. Shared header/footer, the challenge cards, and the guided tour are plain JS modules (assets/js/).

Backend

Firebase (serverless): Firebase Authentication + Firestore Security Rules v2

There is no custom server. Email/password accounts run on Firebase Auth, and firestore.rules does the server-side work: it SHA-256 hashes each submitted flag and compares it against the stored hash, enforces exact point awards, one solve per challenge, the 5-second anti-brute-force throttle, and user/admin roles.

Database

Cloud Firestore (NoSQL)

Users, roles, solves, scores, attempt log, and the hidden flagHashes collection that no client can read. Firebase JS SDK 10.14.1, loaded from gstatic.

Hosting

GitHub Pages, deployed by GitHub Actions; Firebase hosts auth/database

The workflow checks internal links, assembles the site, and publishes to Pages on every push to main. Served at ctf-lab.shoug-tech.com over HTTPS.

Tooling

Visual Studio Code · Git + GitHub

IDE plus Prettier formatting on save, and the Firebase CLI emulators for local testing. Version control on github.com/Shoug-Alomran/cys401; .gitignore keeps the private flag and answer files out of the repo.

5.4 · Challenge Implementation

Challenge 1: The Secret Cyber Clubhouse

Web SecurityEasy100 points
Objective
Discover a hidden invitation code on a simulated cybersecurity club website to unlock the secret room and retrieve the flag.
Security concept
Information Disclosure via HTML Source Code. Demonstrates how developers accidentally expose sensitive details by leaving comments in client-side code.
Challenge design
Built using a single HTML page, CSS for a pastel-themed interface, and client-side JavaScript for code verification. No database or backend server is required for this demonstration.
Hint
“Sometimes, the cutest secrets are hidden where your eyes can’t see them. Have you checked behind the webpage?”

Scenario & execution

Participants navigate to the club login page, which displays a prompt to enter an invitation code.

  1. 1

    Inspection: The participant opens browser developer tools to inspect the webpage’s HTML source code.

  2. 2

    Discovery: They discover an unstripped developer comment containing the invitation code: 

    <!-- Secret club invitation code: •••••••• -->
  3. 3

    Authentication: Entering the code into the invitation code field unlocks the secret message and reveals the flag.

  4. 4

    Completion: The participant submits the flag to the CTF platform to earn 100 points.

The code and flag are hidden on this page so the challenge stays unsolved. Try the lab →

Educational outcome: Teaches participants to inspect HTML source code to identify client-side information disclosure vulnerabilities, reinforcing the critical principle that credentials, access codes, and API keys must never be hardcoded or stored in front-end code.

5.5 · Flag Validation

From submission to score

  1. 01

    Flag storage

    Challenge (CTF) flags will be stored securely on the server as cryptographic hashes to prevent participants from viewing the original flags in the website’s source code.

  2. 02

    Submission processing

    When a participant submits a flag, the server identifies the challenge, normalizes the input, hashes the submitted flag, and compares it with the stored hash.

  3. 03

    Correct & incorrect submission

    If the flag is correct, the system records the completion and awards 100 points. If it is incorrect, the system displays an error message and awards no points.

  4. 04

    Successful submission

    After a correct submission, the system displays a success message and updates the participant’s score.

  5. 05

    Duplicate submissions

    The system checks whether the participant has already completed the challenge. If so, it confirms the existing completion without awarding additional points. A database uniqueness constraint prevents duplicate completion records.

5.6 · Progress Tracking and Scoreboard

Progress and rankings, updated in real time

The platform dynamically calculates user progress and updates leaderboard rankings in real time.

01

Score calculation and points

Each challenge awards a fixed point value. Points are added to the user’s total score upon successful flag validation.

02

Solved challenges and percentage completion

The system keeps track of solved challenges by each account and determines their percentage completion both globally and per track (number of solved challenges out of 12).

03

Scoreboard ranking

The real-time ranking on the scoreboard is done in decreasing order of total points and then using the earliest time stamp of their last correct flag submission.

Section 6

Security Analysis and Controls

How the platform applies the CIA triad, how it identifies, authenticates, and authorizes users, and the controls mapped to every threat from Section 2.

6.1 · CIA Triad

Confidentiality, integrity, availability

C

Confidentiality

Flags, passwords, and each user’s private records (profile, solves, attempts) must stay hidden from other users.

Controls

Flags are stored only as SHA-256 hashes in a database collection that no user can read. Passwords are handled by Firebase Authentication and are not stored in our database. Each user can read only their own profile, solves, and attempts; admins can read all.

I

Integrity

Scores, solves, and challenge content must change only through legitimate actions.

Controls

A score can increase only by the points of a challenge solved in the same transaction. Each challenge can be scored once per user. Solve and attempt records cannot be edited or deleted. Only admins can change challenges and flag hashes. Timestamps are set by the server, not the browser.

A

Availability

Students must be able to reach challenges and submit flags during lab sessions.

Controls

The website is static and hosted on GitHub Pages, and data is stored on Firebase’s managed infrastructure. Each user can submit at most one flag every 5 seconds, which limits flooding through the submission path.

6.2 · Authentication and Authorization

Five access control elements

The platform follows five principles of AAA for access control.

  1. 01

    Identification

    User registration through a unique email address, a case-insensitive username (3–20 characters including letters, numbers, and underscore), and an auto-generated Firebase UID.

  2. 02

    Authentication

    Uses Firebase email/password authentication with email verification and re-authentication for important activities within the account. Also includes a 30-minute session timeout.

  3. 03

    Authorization

    Provides Role-Based Access Control where users have two roles, User and Admin. Administrators perform management actions like management of challenges, flag hashes, and system logs through server-side Firestore security rules, not through hiding of UI elements.

  4. 04

    Auditing

    Logs are automatically created with user ID, challenge ID, value submitted, correctness of the input, hint usage, and server timestamp. Server-side validation is done to avoid fake completion.

  5. 05

    Accounting

    All submission and hint logs are immutable and associated with the user ID and server timestamps for auditing purposes (e.g. flag sharing, brute forcing). Logs remain available even after the user account is deleted.

6.3 · Security Controls

Every threat, mapped to a control

The controls below map the threats and vulnerabilities from Sections 2.2 to 2.4 to the controls implemented in the platform. Control types follow the course classification (preventive and detective).

Brute-force login (2.4) / Weak authentication (2.3)

Preventive

Firebase Authentication blocks sign-in temporarily after repeated failures (“too many requests”). Passwords must be at least 8 characters.

Flag guessing by repeated submissions

Preventive

A server rule allows one submission per user every 5 seconds.

Flag disclosure (2.2) / Insecure flag storage (2.3)

Preventive

Flags are stored only as SHA-256 hashes in a collection no user can read. Pages do not contain plain flags.

Injection / Malicious input (2.2, 2.4)

Preventive

The database is Firestore (NoSQL), accessed through its SDK, so no SQL statements are built from user input. Server rules check input type and length (flags up to 200 characters, usernames by pattern). Usernames are HTML-escaped before display to prevent cross-site scripting.

Broken access control / Unauthorized access (2.2, 2.4)

Preventive

Server rules let users read and change only their own records. Role is fixed to “user” at sign-up. Only admins can write challenges and flags.

Data manipulation of scores and progress (2.2)

Preventive

A score update is accepted only with a new, valid solve in the same transaction. Each challenge scores once per user.

Session misuse on shared lab computers

Preventive

Automatic logout after 30 minutes of inactivity; current password required for sensitive account changes.

Undetected misuse

Detective

Attempts and hints are logged with server timestamps and cannot be edited or deleted. Admins can review them.

Security misconfiguration (2.3)

Detective

Automated tests check the security rules (for example, “nobody can read flag hashes” and “a user cannot promote themselves to admin”).

All controls are technical.

Section 8

Application and Recommendations

Where the platform can be used, who it is for, and four changes that would make it more secure.

8.1 · Practical Application

Where, for whom, and what they practise

Where it can be used

The platform can be used in introductory courses such as CYS401, where an instructor assigns one workshop and its challenges alongside each lecture topic. Student clubs can use it for training days or a small campus CTF, since the scoreboard turns the challenges into a light competition. It can also support awareness sessions for first-year students or non-technical staff, because the Security Awareness and Ethics tracks require no programming.

Who it is for

The main users are university students and beginners with no CTF experience. Everything runs in a web browser, so users do not need to install Linux or use a command line.

What participants practise

Skills from all four tracks: inspecting web pages for exposed information and understanding web vulnerabilities, decoding simple encodings and ciphers, recognizing phishing and weak passwords, and deciding what is authorized and how to disclose vulnerabilities responsibly. The explanation shown after each solve links the flag to the security concept, so users learn the reason behind the answer.

8.2 · Security Recommendations

Four ways to harden the platform

R1

Require email verification before submitting flags

Problem addressed
The 5-second submission limit applies per account. A user could create several accounts with fake emails and guess flags in parallel, or add fake accounts to the scoreboard.
Recommendation
Accept flag submissions only from accounts with a verified email address. Firestore security rules can check the verified status of the signed-in user (Firebase, n.d.-c).
Expected benefit
Creating many accounts becomes slower, and every account on the scoreboard is linked to a real inbox.

R2

Store hashes instead of plain text in the attempts log

Problem addressed
The attempts log stores the exact value each user submitted, including correct flags. Anyone with admin access, or anyone who takes over an admin account, could read the real flags from the log.
Recommendation
Store only the hash of each submitted value, or only whether it was correct.
Expected benefit
The log still supports auditing, but it no longer contains the secrets the platform is built to protect.

R3

Enable multi-factor authentication for admins

Problem addressed
Admin accounts can change roles, edit challenges, and replace flag hashes. A stolen admin password would compromise the integrity of the whole platform.
Recommendation
Enable multi-factor authentication in Firebase Authentication (Firebase, n.d.-a) and require it for every admin account.
Expected benefit
A leaked or phished password alone is no longer enough to take over an admin account. This adds a second authentication factor (something you have), as covered in the course.

R4

Enable Firebase App Check

Problem addressed
The database can be called directly by scripts outside our website, which allows automated flooding (the DoS attack in Section 2.4).
Recommendation
Enable Firebase App Check so the database accepts requests only from our real website (Firebase, n.d.-b).
Expected benefit
Bots and scripts have a harder time abusing the database, which protects availability.

Conclusion

Mini CTF Security Lab Platform succeeds in connecting cybersecurity theory and practice by providing a proper hands-on learning platform. By filling the educational gap in the non-technical security field, the platform combines the main technical aspects (Web Security, Cryptography) with relevant human-centered ones (Security Awareness, Cybersecurity Ethics).

Learning at their own pace

  • Automated flag verification
  • Non-punitive hints
  • Post-solve explanations
  • Progress monitoring
  • Live scoreboard

The key features of the system give participants an opportunity to learn at their own pace and get immediate feedback from the system.

Security built in

  • Cryptographic hashing
  • Input sanitization
  • Access control

The system incorporates basic CYS401 knowledge in terms of application layer security mechanisms to protect itself from injection attacks, broken access control, and data leakage.
