Workshop 01 · Web Security

Break the Web App, Then Learn Why It Broke

How web applications get broken: injection, broken authentication, and data left where anyone can read it. Learn what each flaw looks like and the defensive habit that stops it.

What You’ll Practice

Web challenges cover the flaws that show up most often in real applications — the kind listed in the OWASP Top 10.

01

Injection Flaws

Untrusted input handed straight to a database or command, letting an attacker change what the query does.

02

Broken Authentication

Login and session handling that can be bypassed by editing a cookie, a token, or a request parameter.

03

Exposed Data

Secrets left in page source, comments, backup files, or an API that returns more than it should.

Lesson 1 · WEB-01

Exposed Data: Secrets the Browser Hands Over

Everything a website sends to your browser can be read by you: the HTML, its comments, the JavaScript, and any file sitting in the public web folder. Developers sometimes leave notes, test passwords, API keys, or backup files there, assuming nobody will look.

This falls under security misconfiguration in the OWASP Top 10: the application is not broken in its logic, it is simply deployed with things it should never have shipped.

How it works

Attackers start with the cheapest checks: view the page source, open the browser developer tools, and request files that sites expose by habit, such as robots.txt, .git/, or backup.zip. A robots.txt file asks search engines to skip paths, which also advertises exactly where the interesting files are. 

<!-- TODO: remove before launch. Test account: admin / Winter2024! -->

# robots.txt
User-agent: *
Disallow: /old-backups/

How it is prevented

  • ✓Keep secrets on the server or in a secrets manager, never in client-side code or comments.
  • ✓Strip comments and debug code in the build step, and never deploy backups or the .git folder to the web root.
  • ✓Run secret scanning on the code repository so leaked keys are caught before they ship.

Real-world case

Uber, 2014

According to the US Federal Trade Commission, an Uber engineer posted code containing a company access key on the public site GitHub. The key was used to collect personal data on more than 100,000 drivers, one of the incidents behind Uber’s 2018 settlement with the FTC.

Source: Mintz (2018), summary of the FTC settlement

Quick check

Is a password inside an HTML comment safe because comments are not displayed on the page?

Show answer

No. Comments are not rendered, but they are delivered to every visitor in the page source. Anything sent to the browser is public.

Lesson 2 · WEB-02

Broken Access Control: Trusting the Client

Authentication answers who are you?; authorization answers what may you do? Access control breaks when the application lets the user decide the second question, for example by reading their role from a cookie or a hidden form field the user can edit.

Broken access control is number one in the OWASP Top 10 (2021).

How it works

If a site stores role=guest in a plain cookie and shows the admin panel when it reads role=admin, anyone can open the browser’s storage inspector and change the value. The server never checks. 

Cookie: session=7f3a...; role=guest

// vulnerable server logic
if (request.cookies.role === "admin") showAdminPanel();

How it is prevented

  • ✓Keep the role on the server, tied to the session, and look it up on every request.
  • ✓If a token must travel with the client, sign it (for example a signed session token) so tampering is detected.
  • ✓Deny by default: check permission on the server for every action, not only by hiding buttons.

Real-world case

OWASP Top 10, 2021

OWASP moved broken access control to the top of its list in 2021, reporting that 94% of the applications it tested showed some form of the flaw.

Source: OWASP Top 10 (2021), A01 Broken Access Control

Quick check

A site hides its admin button from normal users. Is the admin page protected?

Show answer

Not by that alone. Hiding a button is a convenience; the server must refuse the admin request from anyone who is not an admin.

Lesson 3 · WEB-03

SQL Injection: When Input Becomes Code

Many applications build database queries from user input. If the input is pasted straight into the query text, the database cannot tell where the developer’s code ends and the user’s data begins, so a crafted input can change what the query does.

How it works

Below, the username is inserted between quotes. Input containing its own quote character closes the string early, and whatever follows is read as part of the SQL command, for example a condition that is always true, or a comment that removes the password check. 

-- vulnerable: input pasted into the query text
query = "SELECT * FROM users WHERE username = '" + username + "'"

-- safe: a parameterized query keeps input as data
query = "SELECT * FROM users WHERE username = ?"
db.execute(query, [username])

How it is prevented

  • ✓Use parameterized queries (prepared statements) for every query that includes input.
  • ✓Give the application’s database account only the permissions it needs (least privilege).
  • ✓Validate input as a second layer, and never show raw database errors to users.

Real-world case

TalkTalk, 2015

Attackers used SQL injection against vulnerable web pages to reach the personal data of 156,959 TalkTalk customers, including bank details for 15,656 of them. The UK Information Commissioner’s Office fined the company a then-record £400,000, calling the technique common and well understood.

Source: BBC News (2016)

Quick check

Does escaping quotes in the input fix SQL injection completely?

Show answer

It helps but is error-prone; it is easy to miss a case. Parameterized queries are the reliable fix because the input is never parsed as SQL at all.

Lesson 4 · WEB-04

Insecure Direct Object References (IDOR)

An IDOR happens when an application fetches a record by an identifier the user supplies, such as an account number in a URL, without checking that this user is allowed to see that record. Being logged in is not the same as owning the data.

How it works

If your profile loads from an address ending in ?id=1001, an attacker simply tries 1000, 1002, and so on. When the server returns whatever it is asked for, every user’s record is one number away. 

GET /api/profile?id=1001   → your profile
GET /api/profile?id=1002   → someone else's profile (should be 403 Forbidden)

How it is prevented

  • ✓On every request, check that the logged-in user owns or may access the requested record.
  • ✓Prefer looking up the record from the session (for example /api/my-profile) instead of trusting an ID from the client.
  • ✓Random identifiers make guessing harder, but they are not a substitute for the ownership check.

Real-world case

First American Financial, 2019

Security journalist Brian Krebs reported that around 885 million mortgage and title documents, some containing bank account and social security numbers, could be viewed by anyone who changed a number in the document’s web address.

Source: KrebsOnSecurity (2019)

Quick check

Record IDs are long random strings instead of 1, 2, 3. Is the IDOR fixed?

Show answer

No. Random IDs only make guessing harder; an ID that leaks (in a link, a log, or an email) still opens the record. The server must check ownership.

What You Take Away

The point of the web track is not the exploit itself but the defensive habit behind it.

  • Validate on the server

    Client-side checks are for convenience. Anything that protects data has to be enforced where the user cannot edit it.

  • Parameterize every query

    Prepared statements remove the ambiguity between code and data that injection depends on.

  • Check authorization per request

    A valid session says who you are, not what you may open. Verify ownership on every object you return.

  • Ship nothing you would not publish

    Comments, debug routes, and backup files in the web root are readable by anyone who looks.
